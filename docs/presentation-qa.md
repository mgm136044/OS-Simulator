# 발표 예상 질문 & 답변 정리

> Process Scheduling Simulator — Thanos 알고리즘 발표 대비
> 대상 시스템: 이미지/영상 렌더링 서버 (예: 유튜브 업로드 트랜스코딩)

## 발표 전략 요약

발표 Q&A는 "주장의 약한 고리"를 미리 찾아 방어선을 구축하는 작업이다. Thanos의 핵심 전제 세 가지를 흔드는 질문이 가장 날카롭다.

1. **remaining_time을 알 수 있다** (= 작업량 사전·진행 중 측정 가능)
2. **soft real-time 시스템이다** (= 1초 늦어도 시스템 안 죽음)
3. **부스트 1회 한정** (= 기아 방지 + 공정성)

교수님은 보통 코드 디테일보다 *설계 결정의 이유*를 묻는다. "구현은 됐는데 왜 그렇게 했는가"에 답할 수 있어야 한다.

## 1. 알고리즘 핵심 메커니즘

| # | 질문 | 답변 방향 |
|---|------|----------|
| Q1 | **부스트 조건이 왜 `remaining ≤ BT/2`인가? 1/3이나 1/4은 안 되나?** | 절반 = "더 많이 진행된 작업"의 가장 직관적 기준. 1/4로 하면 부스트 받는 프로세스가 적어 효과 미미, 3/4로 하면 거의 모든 프로세스가 부스트되어 RR과 차이 없음. 실험적으로 1/2이 균형점. |
| Q2 | **왜 부스트를 1회로만 제한했나?** | 무제한 부스트 시 같은 프로세스가 계속 앞으로 가서 다른 프로세스 기아(starvation) 발생. `boosted` set으로 1회 제한해 공정성 보장. |
| Q3 | **`appendleft`가 아니라 별도 우선순위 큐를 쓰면 더 좋지 않나?** | 우선순위 큐는 O(log n) 삽입, deque는 O(1). 부스트는 "한 번만 빠르게 앞으로 가면 끝"이라 굳이 정렬 자료구조가 필요 없음. 단순함이 디버깅에도 유리. |
| Q4 | **여러 프로세스가 동시에 부스트 조건 충족하면?** | **단일 코어에서는 발생 불가** (한 시점에 한 프로세스만 실행 → quantum boundary 체크 대상도 1개뿐). **멀티코어에서만 발생** — 여러 코어가 같은 tick에 quantum을 끝내며 다수 프로세스가 동시에 ≤ BT/2 충족 가능. 이때 코어 ID 낮은 순(또는 도착 순)으로 순차 appendleft → FIFO 일관성 유지. |
| Q5 | **타임퀀텀=2는 어떻게 정했나?** | 너무 작으면(1) 컨텍스트 스위치 오버헤드, 너무 크면(5+) RR 효과 사라짐. P코어 기준 2 tick = 4 work라 한 번에 적당량 처리 가능. |

### Q4 상세 분석 — 단일 코어 vs 멀티코어

이 질문은 *멀티코어에서만 발생하는 시나리오*다. 단일 코어와 멀티코어의 동작 차이를 정확히 짚어야 점수를 받을 수 있다.

**단일 코어 Thanos 동작:**
```
t=0~2: P1 실행 (P1만 진행) → quantum 끝, P1의 remaining만 체크
t=2~4: P2 실행 (P2만 진행) → quantum 끝, P2의 remaining만 체크
```
- 한 번에 한 프로세스만 실행 → quantum boundary 체크 대상도 1개뿐
- 레디큐 대기 중인 프로세스는 `remaining_time` 변화 없음 → 부스트 조건 새로 충족 불가
- 새 도착 프로세스는 `remaining_time = burst_time` → ≤ BT/2 즉시 불가
- **결론: "동시 부스트 충족"이 구조적으로 불가능**

**멀티코어 Thanos 동작:**
```
t=0~2: core0에서 P1, core1에서 P2 동시 실행
t=2 시점: 두 코어 모두 quantum 끝
  → P1, P2 모두 remaining_time 체크
  → 둘 다 ≤ BT/2 조건 충족 가능
  → 누구를 먼저 appendleft?
```
- 여러 코어가 같은 tick에 동시에 quantum 종료 가능
- 각 코어의 프로세스가 독립적으로 remaining_time 감소
- **다수 프로세스가 동시에 부스트 조건 충족 가능 → 순서 결정 필요**

**해결책:** 코어 ID 낮은 순(또는 도착 순)으로 순차 appendleft → 결과적으로 마지막에 부스트된 프로세스가 맨 앞에 위치. FIFO 일관성 유지.

## 2. 대상 시스템 (렌더링 서버) 정당성

| # | 질문 | 답변 방향 |
|---|------|----------|
| Q6 | **왜 하필 이미지/영상 렌더링 서버인가?** | Thanos가 작동하려면 ① remaining_time을 미리 또는 진행 중 알 수 있어야 함, ② 중간 끊고 재개 가능, ③ soft real-time. 렌더링은 픽셀 수로 작업량 미리 알 수 있고 픽셀/타일 단위 분할 가능, 1초 늦어도 시스템 안 죽음. 세 조건 다 만족. |
| Q7 | **유튜브 같은 실제 시스템도 이런 스케줄러를 쓰나?** | 공개 자료만으로 동일한 스케줄러를 쓴다고 말할 수는 없음. 다만 영상 트랜스코딩처럼 작업량을 추정하고 우선순위를 조정하는 환경을 원리적 비유 대상으로 삼은 것. 본 시뮬레이터는 학습용 단순화 모델. |
| Q8 | **하드 리얼타임 시스템(자율주행, 의료기기)에는 왜 부적합한가?** | Thanos는 부스트로 *평균* 완료시간 단축이 목표. 하드 리얼타임은 *최악(worst-case)* 응답시간이 보장되어야 함. 부스트로 어떤 작업이 우선될지 동적으로 바뀌므로 deadline guarantee 불가. |

## 3. 다른 알고리즘과의 비교 (날카로운 질문)

| # | 질문 | 답변 방향 |
|---|------|----------|
| Q9 | **SPN이 BT를 안다면 더 빠르지 않나? 왜 Thanos가 더 좋은가?** | SPN은 *시작 전* 예상 실행시간이 필요. 렌더링은 픽셀 수×복잡도×씬 종류라 정확한 사전 예측 어려움. Thanos는 *진행 중* 관측한 remaining_time만 사용 → 실측 기반이라 현실적. |
| Q10 | **SRTN과 Thanos는 어떻게 다른가? 둘 다 remaining_time 보는데?** | SRTN: 새 프로세스 도착할 때마다 매 tick 비교, 계속 선점. Thanos: quantum 끝났을 때만 부스트 여부 1회 체크. SRTN은 컨텍스트 스위치 폭증 위험, Thanos는 RR 기반이라 안정적. |
| Q11 | **HRRN도 기아를 방지하는데 Thanos만의 장점은?** | HRRN은 비선점 → 긴 작업 한 번 시작되면 끝까지 점유. Thanos는 RR 기반 선점이라 quantum마다 다른 작업 진행 가능. 응답성(responsiveness)이 더 좋음. |
| Q12 | **그냥 RR이 모든 면에서 충분하지 않나?** | RR은 모든 작업을 동등하게 취급 → 거의 끝난 작업이 새 작업과 같은 대기 시간. Thanos는 "마무리 임박" 작업을 빨리 끝내 *해당 작업의 메모리·자원 즉시 해제*. 평균 TT 단축 + 자원 회전율 증가. |

## 4. 멀티코어 (P-core / E-core) 관련

| # | 질문 | 답변 방향 |
|---|------|----------|
| Q13 | **P코어와 E코어 어떤 기준으로 작업 배정하나?** | 현재 구현: 사용 가능한 코어 중 코어 ID 낮은 것부터(P가 앞). 실제 하이브리드 OS는 작업 크기, 우선순위, 전력 정책 종합 판단. 본 과제는 단순화. |
| Q14 | **P코어가 항상 좋다면 E코어는 왜 있나?** | 전력 효율! P코어 3W/tick, E코어 1W/tick. 가벼운 작업을 E코어에 보내면 같은 시간에 전체 전력 사용량 ↓. 모바일/노트북에서 핵심 가치. |
| Q15 | **시동전력(startup power)이 왜 중요한가?** | 매 컨텍스트 스위치마다 시동전력이 들면 전력 소모 폭증. `_had_idle_tick` 플래그로 *실제 쉰 후*에만 시동전력 부과 → 즉시 재할당 시 절약. 실제 CPU의 sleep state 모델링. |
| Q16 | **P코어 작업의 NTT 계산이 왜 service_time 기준인가?** | P코어는 1 tick에 2 work 처리. BT=6이면 service_time=3 tick. NTT=TT/BT로 하면 0.5 < 1.0이 되어 "빠르게 끝났다"가 음수 의미 → 불가능. service_time 기준이 정상. |

| # | 질문 | 답변 방향 |

| Q21 | **Thanos가 RR보다 *항상* 좋은가? 반례는?** | 아님. 동일 BT에서도 부스트 때문에 실행 순서가 달라질 수 있고, 부스트 받은 작업 뒤의 다른 작업은 대기시간이 늘 수 있음. 워크로드 분포에 따라 trade-off. |

## 가장 위험한 3개 질문 (반드시 준비)

발표 후 Q&A에서 점수가 갈리는 핵심 질문들이다. 솔직하게 한계를 인정하면서도 설계 의도를 방어하는 답변이 핵심.

### 1. Q9 — SPN vs Thanos
> "SPN이 BT를 안다면 Thanos보다 더 빠르지 않나?"

**답변 키워드:** 예측(prediction) vs 관측(observation)
- SPN: 작업 시작 전 정확한 예상 실행시간 필요 → 렌더링에선 사실상 불가능
- Thanos: 진행 중 실제 측정된 remaining_time 사용 → 현실적

### 2. Q21 — RR보다 항상 좋은가
> "Thanos가 RR보다 못한 경우는 없나?"

**답변 키워드:** 워크로드 분포 trade-off
- 동일 BT여도 부스트 때문에 RR과 순서가 달라질 수 있음
- Thanos는 "완료 직전 작업을 한 번 앞당기는 정책"이지 보편 최적 알고리즘이 아님
- 작업 크기가 섞인 워크로드에서 효과가 더 잘 드러남
- "항상 좋은 알고리즘은 없다"는 OS 교과서적 답변

### 3. Q23 — 메모리 절약 측정 여부
> "메모리 절약 효과를 실제로 측정했나?"

**답변 키워드:** 이론적 기대치, 한계 인정
- 본 시뮬레이터에는 메모리 모델 미포함
- 작업 종료 시 즉시 메모리 해제 가정 시 *피크 메모리* 감소 기대
- 실측은 향후 확장 과제

## 답변 시 주의사항

- **우물쭈물 금지**: 한계를 인정할 땐 단호하게, 설계 의도는 자신있게.
- **무리한 옹호 금지**: 측정 안 한 부분을 "측정했다"고 하지 말 것.
- **모르면 모른다**: "현재 시뮬레이터에는 미포함입니다, 향후 과제입니다" 정직 답변이 점수 안전.
- **연결고리 강조**: 항상 *대상 시스템(렌더링 서버)*과 알고리즘 설계가 어떻게 맞물리는지 짚을 것.
